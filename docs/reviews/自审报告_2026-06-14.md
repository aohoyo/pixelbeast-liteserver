## 2. 阻塞级问题（已修复）

> 状态：**两项均已修复并验证**（2026-06-14）。原始问题记录见下，便于追溯。

### ✅ B-01 `monitor` 包编译失败（Critical）— 已修复

**现象**：`go build ./src/...` 与 `go vet ./src/...` 均报错：

```
# pixelbeast/src/monitor
src\monitor\mem_windows.go:12:2: modpsapi redeclared in this block
    src\monitor\mem_release_windows.go:12:2: other declaration of modpsapi
```

**根因**：`modpsapi` 与 `procEmptyWorkingSet` / `procGetProcessMemoryInfo` 在两个文件中重复声明：

| 文件 | 行 | 声明 |
|------|----|------|
| `src/monitor/mem_windows.go` | 12-13 | `modpsapi`, `procGetProcessMemoryInfo` |
| `src/monitor/mem_release_windows.go` | 12-13 | `modpsapi`, `procEmptyWorkingSet` |

两者都是 Windows 构建标签文件，会被同时编入 `monitor` 包，符号冲突。

**影响**：
- `monitor` 包**无法编译** → 所有依赖它的包（`panel` 等）**测试无法运行**（实测 `go test ./src/panel` 报 `build failed`）。
- 生产二进制若只构建 `cmd` 入口可能侥幸通过（因为某些代码路径未被链接），但任何 IDE / CI 跑全包 `vet` 都会失败。

**修复方式**：新建 `src/monitor/psapi_windows.go` 集中声明共享的 `modpsapi` 句柄；`mem_windows.go` 与 `mem_release_windows.go` 改为直接引用它，删除各自的重复声明。

**验证**：`go vet ./src/monitor` exit 0；`go vet ./src/...` exit 0；`go build ./src/...` exit 0；`go test ./src/panel` 由 `build failed` 变为 `ok`。

### ✅ B-02 `file` 包测试在 Windows 上 flaky — 已修复

**现象**：`go test ./src/file` 报：

```
--- FAIL: TestListDirEntries (1.39s)
    TempDir RemoveAll cleanup: ... file1.txt: The process cannot access the file
    because it is being used by another process.
FAIL    pixelbeast/src/file
```

**根因**：`TestListDirEntries`（`src/file/operations_test.go:223-224`）调用 `os.Create(...)` 创建测试文件，但**返回的 `*os.File` 句柄从未关闭**。在 Windows 上打开的句柄会阻止 `t.TempDir()` 在清理时执行 `RemoveAll`，导致 "The process cannot access the file" 失败。（`ListDirEntries` 本身使用 `os.ReadDir`，不持有句柄，问题仅出在测试。）

**修复方式**：测试中循环创建文件后显式 `f.Close()`，并补 `os.Create` 的错误检查。

**验证**：`go test ./src/file -run TestListDirEntries -count=5` 连续 5 次全部通过。

## 5. 代码重复

### 🔴 R-01 JSON Body 解析重复 48 处

**实测**：`src/panel/api_*.go` 中 `json.NewDecoder(r.Body).Decode(&req)` 出现 **48 次**，而已存在的 `parseJSONBody` 工具函数（`src/panel/response.go:130`）仅被调用 **12 次**。

**影响**：每个 handler 都手写 `if err := json.NewDecoder(r.Body).Decode(&req); err != nil { ... }`，5-8 行样板 × 48 ≈ 300+ 行冗余；且错误返回风格不统一（有的 400，有的 500，有的脱敏不彻底）。

**建议**：所有手写解析改为 `parseJSONBody(w, r, &req)`，统一错误响应与日志。

## 6. 错误处理与健壮性

### 🔴 E-01 FTP 传输错误被吞 + 误报成功

**`src/ftp/server.go:725-727`**：

下载中途出错（磁盘满、连接断、限速读失败）会被记录为成功。这是**正确性 bug**，不仅是代码异味。

### 🔴 E-02 `restartServer` 丢弃 re-exec 错误

**`src/panel/api_system.go:1900-1901`**：
```go
exec.Command(os.Args[0], os.Args[1:]...).Start()  // 返回值丢弃

```

若重新拉起新进程失败（路径不存在、权限不足），进程仍 `os.Exit(0)`，服务直接死亡且无任何日志。

**建议**：检查 `Start()` 错误，失败则不退出并返回错误给前端。

## 7. 安全问题

> 注：上版报告（2026-04-23）已修复大量 P0/P1（bcrypt、CSRF、加密、XSS 等），本次仅列**仍存在的缺口**。

### 🟠 S-01 WebSocket 终端 Origin 校验放过空头

**`src/panel/api_terminal.go:23-25`**：
```go
if origin == "" {
    return true  // 无 Origin 头一律放行
}
```

虽然同源浏览器请求通常不带 Origin，但跨站某些场景（如 `<form>` 提交触发的 WS、部分代理）也可能无 Origin 头，存在 CSRF 相邻风险。

**建议**：结合 `Sec-WebSocket-Key` 或会话 Cookie 校验，而非仅看 Origin 是否为空。

---

### 🟡 S-02 `getClientIP` 无条件信任转发头

**`src/panel/handler.go:298-306`**：无条件读取 `X-Forwarded-For` / `X-Real-IP`。

**影响**：登录速率限制（5 次锁定）可被伪造这两个头绕过——攻击者每次请求换个 IP 头即可无限尝试。

**建议**：仅在配置了可信代理（`trusted_proxies`）时才认转发头，否则一律用 `RemoteAddr`。

---

### 🟡 S-03 `notify/` 死代码中的 `InsecureSkipVerify: true`

| 文件:行 | 用途 |
|---------|------|
| `notify/channel.go:57` | SMTP TLS 连接关闭证书校验 |
| `notify/checker.go:33` | 健康检查 HTTP 客户端关闭证书校验 |

虽然当前是死代码，但一旦按 D-01 接入主流程会立即变成活跃风险（中间人攻击）。**接入前必须移除**。

---

### 🟢 S-04 命名误导：`EncryptPassword` 实为 bcrypt 哈希

`src/config/config.go:1051` 函数名 `EncryptPassword`，实际返回 bcrypt 哈希。加密与哈希是不同概念，命名会误导后续维护者。

**建议**：重命名为 `HashPassword` / 增加 `VerifyPassword`。
